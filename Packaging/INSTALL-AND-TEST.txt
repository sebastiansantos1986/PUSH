PUSH REQUESTS
JamfCheckIn reads saved status/progress and sends short-lived target/user-bound update
requests. The privileged worker checks live policy and installation safety. No user
password prompt is used for PUSH requests. They wait until the next worker check,
normally five minutes; an active prompt/workflow may delay them. Use Show current
PUSH notice to respond to an existing recovery popup immediately. Acknowledgements
are not proof of a successful installation. Expired/changed-target requests are rejected.
Pre-existing Jamf check-in/inventory administrator actions remain separate and can
still require administrator approval. Existing Jamf daemon configurations are not
silently altered or newly activated by this client package.

DEADLINE FAILURE RECOVERY
After a failed post-deadline installation, PUSH saves a sanitized failure reason.
The next eligible automatic check presents the recovery notice. Update now requests
an immediate guarded retry. Otherwise the default countdown is 10 minutes. Closing
the window does not reset the saved clock. A displayed notice is required before an
automatic retry. A closed window is retried by a later eligible monitor run, not by
a separate background timer. Logged-out sessions do not get a recovery installation.

Automatic retries re-read live policy and recheck the target, authorization, installer
activity, pending reboot, DDM, meeting policy, disk and power. Repeated failures have
at least 30 minutes between automatic attempts, with a maximum of 3 in a rolling
24 hours (per target). Credentials, signature/version validation and corrupt state
need IT attention; a countdown does not bypass them. Explicit retries still run
preflight. Staging an installer is not a verified successful OS upgrade. A confirmed
restart that misses the required target returns to failure recovery.

YAML OVERRIDES (Admin > User Status & Recovery writes these)
update:
  deadlineRecoveryEnabled: true
  retryCountdownMinutes: 10
  retryBackoffMinutes: 30
  maxAutomaticRetriesPerDay: 3
  allowUserUpdateRequests: true
ui:
  menuBarEnabled: true
The existing update.deadline remains the explicit deadline override. Automatic retry
also requires auto.enabled, no dry-run, and deadline automatic installation enabled.
A fresh installation keeps automation OFF and dry-run ON. Existing settings remain.

STATUS MENU
Reads installed policy, saved results, local progress and monitor status every 30s;
it does not run catalog, Keychain, registration or update checks just by opening.
Shows the target, deadline, next toast and saved failure/recovery progress when present.
Update requests are typed, short-lived, bound to the logged-in user and target and
passed through a private user-owned request file. Root revalidates them. The normal
monitor interval is 5 minutes; an active popup or workflow may delay processing.
Use Show current PUSH notice to return to an existing recovery window and choose
Update now there. Reminder requests cannot postpone a passed deadline or hourly toast.

The installer adds only a user LaunchAgent for the status menu; it starts at the next
graphical login, not during installation. It does not enable the privileged update
monitor. Quit status menu does not stop updates. Disable menuBarEnabled to keep the
status menu off on subsequent launches. LaunchAgent/app removal requires admin deployment.

MANAGED WORKING DIRECTORY
/Library/Management/PUSH/assets/wallpapers

Custom image formats supported by the macOS image picker are normalized into a
static PNG, at most 4096 pixels on the long edge. Original files are not modified.
The normalized image gets a content-addressed filename, such as
noncompliant-<SHA256>.png, to avoid overwriting a different existing background.
Admin stages private copies under the user's Application Support/PUSH Admin/
WallpaperAssets folder and stores only references in the draft, not large image
blobs. Apply copies attached files to protected managed storage before committing
configuration. Export writes attached PNG files alongside YAML; deploy those PNGs
to the managed directory. Imported paths do not magically attach remote assets:
select the image here again or ensure it is already deployed.

The included default is PUSH-NonCompliant.png. A custom image can replace its role
without overwriting that packaged default. Image selection and preview never set
the user's current desktop. Attached-image integrity is rechecked before deployment.

REASSERT WHILE NON-COMPLIANT
Compliance here means running macOS meets the configured numeric macOS target.
This is not proof that every app or cloud-registration requirement is compliant.
Unknown/missing target or running version produces no wallpaper action.

During each eligible live macOS run, the engine queries the console user's active
connected displays through its matching native UI helper. If below target and the
current desktop image is different, the managed non-compliant image is reapplied.
There is no state-transition-only shortcut. A user changing the background does
not stop reapplication on the next eligible check.

No desktoppr installation, private wallpaper database edit, credential collection
or AppleScript control of Finder is used. If the Mac has no desktop session, it is
reassessed later. Dry-run does not change wallpapers. Enforcement is a recurring
visual policy, not a security or cloud-compliance attestation.

RESTORATION
The helper saves a per-user, per-display baseline before replacing the image.
When the target is met, it restores that readable baseline (or the configured
compliant image), only if the current image is still the one PUSH managed. If the
user already changed their image, that choice is preserved and enforcement stops.

Baselines are private to the user under Application Support/PUSH Wallpaper. A corrupt
baseline fails closed instead of overwriting an unknown desktop. A missing/unreadable
original, changing display identities, dynamic/video desktops, additional Spaces,
disconnected displays, privacy restrictions or MDM wallpaper profiles need a pilot
test. The native operation covers active connected displays; it does not claim to
manage every inactive Space. Select a compliant image or restore manually if a
personal original cannot be recovered. Missing baselines are not invented.

Disabling this module stops reapplication. It does not forcibly replace the current
image with an arbitrary personal background.

DELIVERY HISTORY
The new page reads /Library/Management/PUSH/notification-history.json only.
It records new engine observations; old logs are not converted into invented events.
- Requested: a launch was attempted; appearance is not yet proven.
- Displayed: the window readiness signal was received in the console session.
- User response: Install, Later, close, schedule confirmation or support action.
- Timeout: a displayed prompt timed out; it is not mislabeled as Install/Later.
- Completed: a power/restart result that cannot be attributed to a user click.
- Delayed: no desktop, working-hour/meeting restrictions or selected competing work.
- Failed: startup visibility or process failure; no user choice was inferred.

Rows correlate request, display and response by attempt ID. Nonblocking progress
launches remain delivery-unconfirmed unless a visibility signal was captured. A
window appearance is not proof the user read it. Failure/delay retry timestamps are
earliest recheck times, not guaranteed delivery times. Existing policy and service
availability still apply. A stopped monitor cannot record a check it did not run;
use Readiness to inspect actual monitor state.

Engine manual previews are labeled preview and hidden by default; enable the page's
Include engine previews toggle to see them. In-app Studio button checks remain their
separate simulated audit. History is machine-local, capped to recent events, with
repeated identical delay/failure rows coalesced. Reasons omit recognized credential
content; command lines and image originals are not stored. Wallpaper outcomes also
appear, labeled Wallpaper changed rather than notification delivery.

A corrupt/oversized history file is reported unreadable rather than silently reset.
Refresh does not launch a popup, run detection, change a wallpaper, activate a monitor
or install anything. Prior history and managed assets are included in package backup.
