Toast response and design update — November 5, 2026
Developer: Sebastian Santos
Attribution ID: PUSH-DEV-SEBASTIAN-SANTOS

PUSH engine 1.2.3 and PUSH Admin 0.1.4
- Manual popup toast now waits for the actual UI process result rather than
  hard-coding success at launch. Later reports User chose Later; close reports
  User dismissed. Launch failures/timeouts are not labeled as user choices.
- The toast no longer writes a shared /tmp/push-toast-action signal, and
  scheduled checks no longer poll it. A manual popup test cannot request a
  later upgrade through that file. Manual popup never runs InstallWorkflow.
- The scheduled toast controller waits for its own UI result and requests an
  install only on exit 0. Later/close/timeout never consume a toast deferral.
- Scheduled toast handling is now synchronous for that daemon invocation,
  bounded by the existing 15-minute UI wait, rather than fire-and-forget.
- Compact opaque card, short default message, clear version heading, separate
  deadline badge, larger full-width actions, and stronger secondary contrast.
  Light custom accent colors use a dark primary-button label for readability.
- Removed the fake always-present 60-second timer. A countdown only appears
  when toast.autoDismissSeconds is greater than zero, pauses on hover, and
  returns a distinct toast-timeout code (5). Zero/unset stays open until action
  or the controller's maximum wait. The preview timeout is simulated once.
- Custom toast messages and button labels remain configurable. Both apps use
  the same new ToastView layout; custom images and symbols remain supported.

Verification: all Release engine targets and the universal companion compile.
17 isolated response-mapping assertions passed without a UI or app launch.
The combined installer was expanded; versions, signatures, architecture slices,
engine scripts, app-only companion payload, and preservation of config/state
were inspected. No installer, PUSH app, popup, daemon, upgrade, or restart was
launched. Actual click capture, auto-dismiss timing, and visual appearance need

REPAIRS
- Passwords and LAPS secrets are stored through Security.framework, with access
  restricted to the creating executable. Existing entries receive a replacement
  access policy when saved. Local validation uses OpenDirectory; no dscl password
  arguments remain.
- User credentials are read by the same push-ui executable that owns the login
  keychain entry, in the console user's session. The prompt and CLI handoff now
  agree; no plaintext password temporary file is used. Leading/trailing password
  whitespace is preserved.
- startosinstall and softwareupdate receive credentials through stdin, with
  argument arrays rather than interpolated shell scripts. Raw installer output
  and Jamf error response bodies are not logged. Download processes and blocking
  UI execution no longer use predictable temporary executable wrappers.
- System password and LAPS migration edits the correct YAML section and confirms
  the write succeeded. It preserves unrelated settings, removes old multiline
  credential content, and removes duplicate credential scalar fields. Legacy YAML
  credential fallback remains supported for compatibility; migrate deployments
  with auth set-password and jamf set-laps-secret. Do not place credentials in
  command arguments or shell history.
- Prompted console-user credentials retain that username even when localAccount
  names a different admin. Secure Token checks apply to the account actually
  authorizing installation. Missing/invalid required credentials fail closed.
- Native update labels and mist version matching compare complete numeric
  versions; 26.1 cannot match 26.10. Full installers require matching product OS
  metadata, never their unrelated application bundle version. Modern installer
  metadata can be inspected from SharedSupport.dmg mounted read-only. Unknown,
  conflicting, incomplete, or wrong-version installers are rejected. Gatekeeper
  assessment is required before executing startosinstall; --usage is not treated
  as a signature check. Existing installers are never deleted on probe failure.
- Installation state is persisted before launch. A kernel-held lock prevents
  overlapping workflows. Failed launches/nonzero exits clear pending state;
  successful staging waits for reboot and running-OS verification. The original
  target and boot timestamp are retained. A reboot below target releases retry
  state without marking completion. Completion is reported once. Auto-check does
  not schedule another workflow while one is pending.
- Installation and auto-check dry runs stop before prompting, downloading,
  credentials, installation state changes, or reboot actions. Auto-check dry-run
  now prints a no-action summary instead of polling or executing the schedule.
- Progress files use a verified root-owned runtime directory under
  /private/var/run/com.push. Child output is drained before waiting, preventing
  pipe-buffer deadlocks; retained output is bounded. Installation progress uses
  actual output rather than an invented countdown to reboot.
